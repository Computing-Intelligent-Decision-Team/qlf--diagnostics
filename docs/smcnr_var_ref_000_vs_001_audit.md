# SMCNR var_ref_000 PASS vs var_ref_001 FAIL Audit

**Date**: 2026-06-23
**Status**: Runner not calibrated — batch_0002 W/L results invalid for sizing conclusions

## 1. Executive Summary

`var_ref_000` (multi sweep) passed with DRC=0, LVS=yes, PEX=37.
`var_ref_001` (batch_0002) failed at `mos_only_projection_lvs`.

Both use **exact cand_0031 sizing** — identical W/L/multi/nf/passive parameters.
The only differences are:

| Dimension | var_ref_000 (PASS) | var_ref_001 (FAIL) |
|-----------|-------------------|---------------------|
| Netlist format | `l=10u`, `lr=4e-6` | `l=10.0u`, `lr=4.0e-6` |
| `MAGICAL_ADD_LOCAL_VDD_STRIPE_BELOW_PASSIVES` | **0** (OFF) | **1** (ON, hardcoded coords) |
| `lvsNetRenames` source | Auto-discovered by harness controller | Hardcoded from var_ref_000 |
| Runner | Harness controller (`LayoutVerificationAdapter.run()`) | Manual shell pipeline |

## 2. Detailed Comparison

### 2.1 Netlist

```
var_ref_000:  l=10u w=1.5u ..., lr=4e-6 wr=400e-9 ...
var_ref_001:  l=10.0u w=1.5u ..., lr=4.0e-6 wr=400.0e-9 ...
```

Same values, different numeric formatting. Both are valid SPICE.
Unlikely to cause MAGICAL behavioral difference.

### 2.2 Config JSON

Identical except for `hspice_netlist` filename. Same PDK paths, same
`lvsNetRenames` (after we added them to var_ref_001).

### 2.3 MAGICAL Env Vars

| Env var | var_ref_000 | var_ref_001 |
|---------|------------|------------|
| `MAGICAL_ADD_LOCAL_VDD_STRIPE_BELOW_PASSIVES` | **0** | **1** |
| `MAGICAL_LOCAL_VDD_STRIPE_HEIGHT_DBU` | not set | 200 |
| `MAGICAL_LOCAL_VDD_STRIPE_Y_DBU` | not set | 13200 |
| `MAGICAL_LOCAL_VDD_STRIPE_EXCLUDE_X_DBU` | not set | "3000:3450,..." |

**Critical**: var_ref_000 passed WITHOUT the pre-route VDD stripe. Our
var_ref_001 had it enabled with coordinates from the SMCNR YAML config,
which were tuned for the upstream layout dimensions (~62K DBU wide chip).
The local MAGICAL run produces a ~34K DBU wide chip. The hardcoded stripe
coordinates may conflict with the actual placement.

### 2.4 Runner

| Aspect | var_ref_000 | var_ref_001 |
|--------|------------|------------|
| Invocation | Harness controller via `LayoutVerificationAdapter.run()` | Manual `bash run_sky130_case_pipeline.sh` |
| `lvsNetRenames` discovery | Auto via `sky130_case_pipeline_helpers.py` | Hardcoded copy from var_ref_000 |
| MOS-only projection | Generated by `write-mos-projection` helper | Generated by same helper (pipeline step) |
| MAGICAL Docker | Same image, with harness-provided env | Same image, with manual env vars |

### 2.5 Pipeline Failure Point

var_ref_001 failed at `mos_only_projection_lvs` — the second MAGICAL pass.
This pass creates a fresh MOS-only netlist, runs MAGICAL again, and attempts
LVS. The failure log shows:

```
FAIL[mos_only_projection_lvs]: MOS-only projection pipeline failed
```

The LVS projection sub-pipeline likely failed because:
- The second MAGICAL run produced a GDS with anonymous node names different
  from the hardcoded `lvsNetRenames`
- Or the second run's extraction collapsed (equiv gnda-vdda)

## 3. Root Cause Assessment

The multi sweep's var_ref_000 was run through the **harness controller**,
which:
1. Uses `SpiceCandidateCompiler` to generate the netlist
2. Calls `LayoutVerificationAdapter.run()` which invokes
   `run_sky130_case_pipeline.py` (Python wrapper)
3. The Python wrapper passes all env vars from the YAML config
4. The pipeline auto-discovers `lvsNetRenames` from the first MAGICAL pass
5. The second LVS pass uses the auto-discovered renames

Our batch_0002 used **manual shell pipeline invocation** which:
1. Uses hand-generated SPICE netlist
2. Uses hardcoded `lvsNetRenames` copied from var_ref_000
3. Has `MAGICAL_ADD_LOCAL_VDD_STRIPE_BELOW_PASSIVES=1` with coordinates
   tuned for a different chip geometry
4. The second LVS pass uses hardcoded renames that may not match

## 4. Impact on Batch_0002 Results

**ALL batch_0002 results (6/6 FAIL) are invalid for sizing conclusions.**

The exact-repeat baseline (`var_ref_001`) failed, confirming the runner
is not calibrated to the known-good pipeline. The W/L perturbation failures
cannot be distinguished from runner failures.

## 5. Calibration Required

Before any W/L perturbation can be assessed:

1. **Replicate the exact multi sweep runner**: Use harness controller
   (`LayoutVerificationAdapter.run()`) or `run_sky130_case_pipeline.py` 
   Python wrapper, not the raw shell script.
2. **Do NOT set `MAGICAL_ADD_LOCAL_VDD_STRIPE_BELOW_PASSIVES=1`**: The
   working var_ref_000 had it OFF. The pre-route stripe is NOT required
   for this topology.
3. **Let the pipeline auto-discover `lvsNetRenames`**: Hardcoded renames
   from a different MAGICAL run may not match.
4. **Verify exact repeat passes first**: Only after `var_ref_00X` passes
   with the calibrated runner, proceed to W/L perturbation.
