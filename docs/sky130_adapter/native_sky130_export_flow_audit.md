## Focused Findings

- `flow/python/MagicalDB.py` reads the JSON-selected netlist and simple techfile, then marks power nets from `vddNetNames` / `vssNetNames`.
- `flow/python/PnR.py` invokes Anaroute with `parseLef`, `parseTechfile`, `parseGds`, `writeLayoutGds`, and `writeDumb`.
- `anaroute/src/writer/wrLayout.cpp` merges placement GDS with routing geometry and writes final `*.route.gds`; this is the most direct native export hook for route shapes and route TEXT.
- `anaroute/src/writer/wrLayout.cpp` currently writes routing polygons using `maskIdx = _cir.layerIdx2MaskIdx(...)` and datatypes `0` or `40`; route IO text uses `100 + maskIdx` and no Sky130 TEXTTYPE.
- `flow/cpp/magical_flow/src/writer/GdsWriter.h` writes layout rectangles through `TechDB::dbLayerToPdk` and preserves per-rectangle datatype; it also writes TEXT with skipped datatype/texttype semantics.
- `anaroute/src/writer/wrDumb.cpp` writes the `*.ioPin` file from all routed nets, choosing one box/layer per net. It does not know the original top subckt port list.
- `tools/sky130_adapter/remap_gds_to_sky130.py` is currently an external binary GDS layer/datatype remapper; its responsibility belongs near native GDS export, not in Magic/LVS scripts.
- `tools/sky130_adapter/add_sky130_pin_labels_from_iopin.py` and `add_sky130_pin_shapes_from_iopin.py` currently compensate for missing native Sky130 pin-purpose/text export.
