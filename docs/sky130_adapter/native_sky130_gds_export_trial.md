# Native Sky130 GDS Export Trial

## Scope

This is Native Sky130 Export Phase 1.5.  It makes Anaroute's final route GDS
export optionally rewrite confirmed drawing/well/implant/contact/via
layer/datatype pairs to Sky130 GDS numbers.  It does not yet make MAGICAL a
complete native Sky130 PDK flow, and it does not replace the existing
bridge/remap regression flow.

Native pin labels and pin-purpose geometry are intentionally deferred to the
next phase.

## Writer Changes

- `anaroute/src/writer/wrLayout.cpp`
- `anaroute/src/writer/wrLayout.hpp`
- `flow/python/PnR.py`

`wrLayout.cpp` is the route GDS export point reached through
`router.writeLayoutGds(...)`.  The writer now checks the optional environment
variable:

```bash
MAGICAL_GDS_EXPORT_MAP=/path/to/sky130_anaroute_gds_export.map
```

When the variable is unset, the old writer behavior is unchanged.

When the variable is set, the writer reads a simple whitespace-separated map:

```text
# input_layer input_datatype output_layer output_datatype name
3 0 64 20 nwell.drawing
6 0 65 20 diff.drawing
17 0 66 20 poly.drawing
25 0 94 20 psdm.drawing
26 0 93 44 nsdm.drawing
30 0 66 44 licon1.drawing
```

The writer remaps polygon/path/rectangle shapes in the full GDSDB just before
the final GDS is written.  This includes both the placement GDS already read by
Anaroute and the routing shapes added by Anaroute.  Text records are counted in
the writer report but left unchanged in Phase 1.5.

`PnR.py` has one opt-in guard: when `MAGICAL_GDS_EXPORT_MAP` is set, it skips
the post-route internal `ckt.parseGDS(route.gds)` call.  That parser expects
MAGICAL internal layer IDs, so it cannot safely read the Sky130-native route GDS
back into the MAGICAL internal TechDB.  The default path still performs the old
parse.

## Inverter Native Trial

Run:

```bash
tools/sky130_adapter/run_inverter_sky130_native_export_trial.sh
```

The wrapper:

1. Generates the Anaroute export map.
2. Builds `anaroutePy` from the current source into
   `generated/sky130_native_trial/anaroute_build`.
3. Runs MAGICAL on a generated inverter work directory with
   `MAGICAL_GDS_EXPORT_MAP` set.
4. Copies the native route GDS to
   `generated/sky130_native_trial/inverter/inverter_core.native.route.gds`.
5. Inspects GDS layer/datatype pairs.
6. Runs Magic DRC and an extraction probe.

The wrapper does not call `remap_gds_to_sky130.py`.

## Why Pin Postprocess Is Still Needed

The native writer still leaves MAGICAL IO text on legacy text layers such as
`131/0` and `136/0`.  It does not yet emit Sky130 layer-specific label purposes
or pin-purpose geometry.  LVS-quality extraction therefore still needs the
existing pin label/shape postprocess until Phase 2 moves that logic into the
native export path.

## Next Step

Native pin export should move the current postprocess responsibilities into the
export layer:

- Read the top-port list from the MAGICAL source netlist or a passed top-port
  set.
- Filter `ioPin`/IO geometry so internal routed nets are not promoted to ports.
- Emit layer-specific Sky130 label records, such as `li1.label 67/5`.
- Emit layer-specific Sky130 pin-purpose geometry, such as `li1.pin 67/16`.

This must remain opt-in until it is proven not to disturb the existing mockPDK
and bridge/remap flows.
